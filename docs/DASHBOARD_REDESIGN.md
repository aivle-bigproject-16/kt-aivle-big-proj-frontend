## 1. 현행 요소 분해

### 1.1 화면 계층

현재 앱의 전역 구조는 아래와 같다.

- `RootLayout` — `justify-content: center`, 3열 고정
  - `.root-layout__left` (22.2857rem) — `SideBar`
  - `.root-layout__center` (120rem) — `Outlet`, 라우트별 페이지
  - `.root-layout__right` (22.2857rem) — **내용물 없는 빈 태그**

우측 컬럼은 중앙 정렬을 맞추기 위한 스페이서로만 존재하며, 화면 폭의 약 13%가 아무것도 그리지 않는다.

`DashboardPage`는 세로 4개 섹션으로 구성된다.

- `.dashboard__sim-nav` (120rem × 4.2857rem) — `SimNavBar`, 5개 탭 + 제어 버튼
- `.dashboard__simulation` (120rem × 43rem) — 패널 5장을 가로로 이어붙인 캐러셀
- `.dashboard__kpi` (120rem × 17rem) — `KpiCards`, 카드 3장
- `.dashboard__result` (120rem × 26rem) — `ResultSummary`, 파이차트 + 테이블

### 1.2 데이터 소스 매핑

**현행 대시보드의 4개 섹션은 전부 같은 하나의 데이터 소스를 먹는다.**

| 섹션 | 컴포넌트 | 데이터 출처 |
|---|---|---|
| 시뮬 네비 | `SimNavBar` | 로컬 `useState` (탭 인덱스) |
| 시뮬 패널 5장 | `Overview` / `Pending` / `Capture` / `Analyze` / `Complete` | `useSimulationStore` (WS `/ws/sim`) |
| KPI | `KpiCards` | `useSimulationStore` (WS) |
| 결과 요약 | `ResultSummary` | `useSimulationStore` (WS) |

`useDashboardStore`(HTTP `POST /dashboard`)는 `DashboardMockPanel`만 참조하고, 그 Mock 패널은 어느 라우트에도 마운트되지 않는다. `DefectAnalysisChart` 역시 `index.ts`에서 export만 되고 사용처가 없다.

즉 **누적 통계 대시보드는 화면에 존재하지 않는다.** 현재 "대시보드"라 불리는 것은 전부 시뮬레이션 실시간 모니터다. 코치의 F11("대시보드랑 공정라인이 겹쳐 보인다")은 착시가 아니라 정확한 관찰이다.

### 1.3 중복 매트릭스

같은 데이터가 한 화면에서 몇 번 표현되는지 정리한다.

| 정보 | 표현 1 | 표현 2 | 표현 3 |
|---|---|---|---|
| 대기 셀 수 | `OverviewPanel` PENDING 미니카드 | `PendingPanel` 정보 카드 (탭 이동) | — |
| 촬영 셀 수 | `OverviewPanel` CAPTURE 미니카드 | `CapturePanel` 정보 카드 (탭 이동) | — |
| 분석 중 셀 | `OverviewPanel` ANALYZE 카드 | `AnalyzePanel` (탭 이동) | — |
| 완료 셀 분포 | `OverviewPanel` COMPLETE 3행 | `CompletePanel` 서브카드 3장 (탭 이동) | `ResultSummary` 파이차트 |
| 공정 상태 | `KpiCards` Process Status | `AnalyzePanel` 상태 라벨 | — |

`OverviewPanel`은 사실상 나머지 4개 패널의 축소판이다. 여기에 KPI와 결과요약이 같은 수치를 세 번째로 반복한다.

### 1.4 전체탭의 시각 덩어리 개수

현재 '전체' 탭 한 화면에 형태가 서로 다른 블록이 12개 이상 놓인다.

- `SimNavBar` — 탭 트랙, 제어 버튼 (2)
- `OverviewPanel` — PENDING 미니카드, CAPTURE 미니카드, NEXT 배지, CURRENT 배지, ANALYZE 카드(수치 2개 + 배터리 SVG), COMPLETE 카드(PASS/REJECT/FAIL 3행) (6)
- `KpiCards` — 카드 3장 (3)
- `ResultSummary` — 파이 카드, 테이블 카드 (2)

F1("글이나 그림이 구분이 많이 돼서 혼란스러움")의 원인은 정보량이 아니라 **형태의 가짓수**다. 블록마다 크기·모서리·배치 규칙이 달라 눈이 매번 새로 적응해야 한다.

### 1.5 상태색 불일치

같은 의미에 서로 다른 색이 쓰이고 있다.

| 의미 | `CompletePanel` / `OverviewPanel` | `ResultSummary` |

`SideBarTab`은 `label` prop을 받지만 `title` 속성(마우스 오버 툴팁)으로만 사용하고 화면에는 아이콘만 렌더링한다. F8·F9가 지적한 지점이다.

## 2. 재설계 원칙

### 2.1 시제로 화면을 나눈다

전체탭은 위아래로 시제가 갈린다.

- **위 (flow)** — 현재형. 지금 흐르고 있는 것. 대기 · 촬영 · 분석.
- **아래 (결과 블록)** — 완료형. 이미 나온 결과. PASS · REJECT · FAIL.

flow 내부에는 결과 집계를 두지 않는다. 결과 표현은 하단 한 곳으로 일원화한다. 이 원칙 하나로 F10과 F11이 동시에 닫힌다.

### 2.2 껍데기를 통일하고 내용물만 차등한다

F1의 원인은 형태의 가짓수다. 정보를 줄이는 대신 **형태를 묶는다.**

- flow 노드 3개는 크기·모서리·내부 슬롯 구성이 완전히 동일하다. 슬롯 안에 들어가는 값만 단계별로 다르다.
- 세부 탭 4개는 "요약 바 + 목록" 한 가지 골격을 공유한다. 목록 영역의 내용만 다르다.

껍데기가 같아야 옆으로 늘어놓았을 때 라인으로 읽힌다. 크기가 제각각인 카드를 나열하면 라인이 아니라 카드 나열이다.

### 2.3 메인은 크기가 아니라 밀도로 구분한다

'전체'와 나머지 4탭은 성격이 다르다. 전체는 실시간 flow 개요이고, 4탭은 세부 드릴다운이다. 이 위계는 탭 버튼을 키워서가 아니라 **구성 밀도**로 표현한다.

- 전체탭 — 헤더 + flow 레인 + 결과 블록. 3덩이.
- 세부 탭 — 요약 바 + 목록. 2덩이. 하단 KPI·결과요약 없음.

### 2.4 한 정보는 한 화면에 한 번만 그린다

§1.3의 중복 매트릭스를 0으로 만든다. 같은 수치가 두 번 나오면 둘 중 하나는 삭제하거나 다른 화면으로 옮긴다.

### 2.5 참조 아티팩트의 지위

`Live Monitoring Flow 재설계 명세`(2026-07-27 작성)는 **방향 참고용**이다. 다음 두 가지 이유로 그대로 이식하지 않는다.

- 결함 목록(D1~D10)과 구현 순서가 `Simulation.tsx` 기준인데, 그 컴포넌트군은 현재 어디에도 마운트되지 않는다. 현재 '전체'는 `OverviewPanel`이다.
- 디자인 언어가 repo와 다른 계열이다. 아티팩트는 "얇은 테두리 + 작은 라운드 + 그림자 없음"인 콘솔 계열이고, repo는 "테두리 없음 + 큰 라운드 + 표준 그림자"인 소프트 카드 계열이다. 섞으면 둘 다 무너진다.

**승계하는 것** — 노드 껍데기 통일, 셀 타일 스트립, 누적 100% 바 + 범례 3분할, 상태 5색 체계, 실행 상태 3종(idle/running/completed), 모션 절제 원칙.

**폐기하는 것** — 1px 테두리 + 좌측 3px 스트라이프, 10px 라운드, 1580px 기준 치수, flow 내부 결과 블록, D 결함 ID와 10단계 구현 순서.

### 2.6 repo 디자인 언어 준수

새로 그리는 모든 카드는 repo의 기존 언어를 따른다.

| 항목 | 값 | 근거 |
|---|---|---|
| 카드 배경 | `#ffffff` | 현행 전 컴포넌트 공통 |
| 바닥 배경 | `#ededed` (`--bg`) | `index.css` |
| 테두리 | **사용하지 않음** | 현행 `border: none` 6회, 실선 테두리 사실상 부재 |
| 라운드 | **5단계 스케일, 상한 15px** — §2.7 참조 |
| 그림자 | `0 2px 8px rgba(0, 0, 0, 0.25)` | 현행 15회. `ARCHITECTURE.md` 표준값 |
| 본문 텍스트 | `#191c1d` | 현행 최다 |
| 보조 텍스트 | `#5b5f63` | 현행 최다 |

카드 간 구분은 테두리가 아니라 **흰 배경 + 그림자 + 여백**으로 만든다.

### 2.7 라운드 스케일

라운드는 5단계로 고정하고 **상한을 15px** 로 둔다. 판정 기준은 값이 아니라 **높이 대비 비율**이다.

| 토큰 | 값 | 대상 |
|---|---|---|
| `--r-xs` | `2px` | 셀 타일, 진행바 (h ≤ 6) |
| `--r-sm` | `4px` | 누적 바, 스켈레톤 바, 작은 마커 |
| `--r-md` | `8px` | 버튼, 페이지네이션, 목록 행, 썸네일, 그룹 헤더 |
| `--r-lg` | `12px` | 중간 카드 — 탐지 카드, 서브 블록, 캔버스 영역 |
| `--r-xl` | `15px` | **최상위 카드 (상한)** — 테이블 카드, 요약 바, 헤더, flow 노드, KPI |
| `--r-pill` | `999px` | 칩, 배지, 토글, 사용자 칩, 탭바 트랙·인디케이터 |

**판정 규칙** — 요소의 `rx`가 높이의 절반 이상이면 캡슐이 의도이므로 `--r-pill`을 쓴다. 그렇지 않으면 위 스케일에 상한 15를 적용한다. 필터 칩(h32)에 15를 주면 캡슐이 되다 만 애매한 형태가 되므로 pill은 상한 대상이 아니다.

**중첩 라운드 규칙** — 안쪽 요소의 라운드는 바깥보다 작아야 동심으로 보인다. 카드(15) 안의 목록 행은 8, 그 안의 배지는 pill이다. 같은 값을 중첩하면 안쪽이 더 둥글어 보여 어긋난다.

**폐기된 값** — 기존 코드의 `2.4rem`(24)과 피그마 6/7 환산 잔재(`23.4` · `21.4` · `18.8` · `17.1` · `16.4`)는 모두 위 스케일로 흡수한다. 사이드바 탭(h56, r16.4)과 내비 컨테이너(h240, r18.8)는 비율이 각각 0.29·0.08이므로 카드로 보아 `15`, 탭바 트랙(h42.9, r21.4)과 인디케이터(h34.3, r17.1)는 비율이 정확히 0.5이므로 `pill`이다.

## 3. 전역 프레임

### 3.1 3열 구조 유지

`RootLayout`의 3열 구조와 총 폭은 유지한다. 다만 우측 컬럼이 더 이상 빈 스페이서가 아니다.

- `.root-layout__left` (22.2857rem) — 사이드바
- `.root-layout__center` (120rem) — 페이지
- `.root-layout__right` (22.2857rem) — **사용자 블록 (신설)**

좌우로 관심사가 갈린다. 왼쪽은 "이 서비스는 무엇이고 어디로 갈 수 있는가", 오른쪽은 "나는 누구이고 어떻게 나가는가"를 담당한다.

### 3.2 사이드바 — 로고와 슬로건

로고 카드와 하단 pill의 `margin-left: 8.5714rem`(우측 밀어내기)을 제거하고 컬럼 안에서 중앙 정렬한다. 확보되는 좌측 공간을 라벨과 슬로건이 사용한다.

| 요소 | 치수 | 비고 |
|---|---|---|
| 로고 카드 | 8.5714rem 정사각 | 라운드 `15px`(§2.7), 표준 그림자 |
| 슬로건 | 폭 19rem, 1~2줄 | 로고 카드 하단, 위쪽 여백 1.2rem |

슬로건 문구는 이 문서에서 확정하지 않는다. 팀에서 정할 자리이며, **자리와 글자 수 상한만** 규정한다.

- 1줄 기준 한글 12~16자
- 2줄까지 허용, 3줄 이상은 로고 블록이 메뉴를 아래로 밀어내므로 금지
- 폰트 크기 1.2rem, 색상 `#5b5f63`, 가운데 정렬

### 3.3 사이드바 — 탭 라벨

아이콘과 라벨을 **가로로** 배치한다. pill 폭을 8.5714rem(85.7px)에서 **19rem(190px)** 으로 넓혀 비어 있던 좌측 공간을 흡수한다.

폭 계산은 아래와 같이 성립한다.

| 항목 | 값 |
|---|---|
| 사이드바 컬럼 | 222.86px |
| 좌우 패딩 (`1.0629rem` × 2) | 21.26px |
| 가용 폭 | 201.6px |
| pill 폭 | 190px |
| 여유 | 11.6px |

탭 하나의 내부 구성은 다음과 같다.

| 슬롯 | 폭 | 비고 |
|---|---|---|
| 좌측 패딩 | 1.6rem | |

### 3.4 우측 사용자 블록

우측 컬럼 최상단에 **고정(sticky)** 배치한다. 스크롤해도 제자리에 남는다.

**형태 제약이 있다. 가로로 긴 바를 만들면 안 된다.** 가로 바를 만들면 F5("상단바도 있고 밑에도 있고 겹치는 것 같음")를 새로 만드는 꼴이 된다.

- 접힌 상태 — 아바타 원형 + 사용자 이름. 칩 하나. 폭 최대 19rem, 높이 4.2rem
- 펼친 상태 — 칩 클릭 시 아래로 드롭다운. 역할(`role`) 표시 + 로그아웃 버튼

| 항목 | 값 |

| 상단 여백 | 3rem (사이드바 로고 카드와 수직 정렬) |
| 아바타 | 3.2rem 정사각, 원형 |
| 이름 | 1.4rem, `#191c1d` |

`TopAppBar`는 마운트하지 않는다. 검색·알림 기능은 대응하는 백엔드가 없어 껍데기이며, 상단 바를 하나 더 만드는 것은 F5와 정면으로 배치된다.

## 4. 전체탭

### 4.1 전체 골격

세로 3덩이로 구성한다.

- **헤더** — 타이틀 · 실행 상태 배지 · Sim Control
- **flow 레인** — 대기 → 촬영 → 분석. 노드 3개 + 커넥터 2개
- **결과 블록** — 헤더(완료 수 · 양품률) + 누적 100% 바 + 범례 3분할 + 탐지 카드 스트립

현행 12개 이상에서 3개로 줄어든다.

### 4.2 헤더

| 슬롯 | 내용 | 정렬 |
|---|---|---|
| 좌측 | `Live Monitoring Flow` 타이틀. 1.8rem / 700 | 좌 |
| 우측 | 실행 상태 배지 + `Sim Control` 버튼 | 우 |

실행 상태 배지는 WS 연결 상태(`WsStatus`)와 시뮬레이션 진행 상태(`SimulationRunStatus`)를 함께 표현한다. 자세한 조합은 §9를 따른다.

`Sim Control` 버튼은 현행 `SimNavBar`의 원형 회색 버튼(`.sim-nav__control`)을 대체한다. 현행 버튼은 아이콘도 라벨도 없어 무엇인지 알 수 없다. 텍스트 라벨을 가진 버튼으로 바꾸고, 클릭 시 현행 `SimControlPanel`(배치 사이즈 · 사진 수 · 촬영 속도 · 시작)을 팝오버로 연다.

### 4.3 flow 레인

**노드 3개를 수평 1열로 배치하고 커넥터로 잇는다.** 완료는 노드가 아니라 아래 결과 블록이 담당한다.

#### 4.3.1 치수

좌우 패딩을 현행 `8.5714rem`(85.7px)에서 **`2rem`(20px)** 으로 줄인다. 현행 패딩은 콘텐츠 폭의 14%를 차지하며, flow 레인은 폭을 끝까지 써야 라인으로 읽힌다.

| 항목 | 값 (px) | 값 (rem) |
|---|---|---|
| 콘텐츠 영역 (`--col-main`) | 1200 | 120rem |
| 좌우 패딩 | 20 × 2 | 2rem × 2 |
| 가용 폭 | 1160 | 116rem |
| 노드 카드 | 360 × 200 | 36rem × 20rem |
| 커넥터 | 40 × 20 | 4rem × 2rem |
| 합계 검산 | 360×3 + 40×2 = **1160** | 정확히 일치 |

이 패딩 값은 **5개 탭 공통**으로 적용한다. 탭 전환 시 좌우 정렬이 튀지 않아야 한다.

#### 4.3.2 노드 카드 슬롯 구조

3개 노드가 아래 5슬롯을 **완전히 동일하게** 갖는다. 슬롯의 위치·높이·정렬은 고정이고, 채워지는 값만 다르다.

| # | 슬롯 | 내용 | 타이포 |
|---|---|---|---|
| 1 | 헤더 | 상태 점 + 단계명(한글) + 영문 코드 + 우측 아이콘 | 한글 1.4rem/600, 영문 1.05rem mono |
| 2 | 대표 수치 | 큰 숫자 + 단위 + 우측 보조 정보 | 숫자 3.2rem/700, 단위 1.5rem |
| 3 | 진행바 | 높이 0.4rem, 라운드 999 | — |
| 4 | 셀 타일 스트립 | 6 × 16px 타일, gap 3px | — |
| 5 | 푸터 | 좌측 보조 텍스트 + 우측 배치 정보 | 1.15rem mono |

카드 내부 좌우 패딩은 1.8rem(18px)이므로 스트립 가용 폭은 324px이다. 타일 피치가 9px(타일 6 + gap 3)이므로 **노드당 최대 36개**를 표시한다. 초과분은 스트립 끝에 `+196` 형식으로 표기한다.

**타일 크기는 셀 수와 무관하게 고정한다. 개수만 자른다.** 타일이 늘었다 줄었다 하면 오히려 읽기 어렵다.

#### 4.3.3 노드별 내용

| 노드 | 대표 수치 | 보조 정보 | 진행바 의미 | 타일 스트립 | 푸터 |
|---|---|---|---|---|---|
| 대기 PENDING | `registered` 개수 | `/ 240 total` | 잔여 비율 | 뉴트럴 타일, 큐 선두 36개 | 다음 배치 번호 |
| 촬영 CAPTURING | 현재 배치 셀 수 | `배치 6셀` | 촬영 속도만큼 0→100% 타이밍 진행 | `CAPTURING`은 진한 파랑 깜빡임, `CAPTURED`는 흐린 파랑 고정 | 현재 배치 번호 |
| 분석 ANALYSIS | `analyze` 유무 (0 또는 1) | `셀 #1032` | 미사용(0 고정) | 스트립 대신 스피너 + `AI 추론 진행 중` | 현재 배치 번호 |

분석은 동시에 한 셀뿐이므로 타일 스트립이 의미가 없다. 슬롯 자리는 유지하되 스피너와 문구로 채운다. **슬롯을 비우거나 없애지 않는다** — 껍데기 통일이 무너진다.

#### 4.3.4 커넥터

화살촉을 가진 SVG 선으로 그린다. 다음 단계가 활성일 때만 흐름 애니메이션이 돈다(§7.3).

- 비활성 — `#cfd4d9` 실선 1.5px
- 활성 — 진행 청록 `#13777C`, `stroke-dasharray: 5 5`, `stroke-dashoffset` 애니메이션

### 4.4 결과 블록

**KPI 카드 3장은 폐기하고 이 블록의 헤더로 흡수한다.** §1.3에서 확인했듯 3장 모두 flow 또는 결과 블록과 중복된다.

| 폐기되는 KPI | 중복 대상 |
|---|---|
| Process Status | 전체탭 헤더의 실행 상태 배지 (§4.2) |
| Total Inspections | 대기 노드의 `/ 240 total` (§4.3.3) |
| Yield Rate | 결과 블록 헤더로 흡수 (아래) |

블록 구성은 위에서 아래로 다음과 같다.

**(1) 헤더**

| 슬롯 | 내용 | 타이포 |
|---|---|---|
| 좌측 | `검사 결과` + `RESULT` | 1.4rem/600 + 1.05rem mono |
| 우측 | `완료 128 / 240` · `양품률 96.1%` | 숫자 1.7rem/700, 라벨 1.3rem |

양품률은 flow가 표현할 수 없는 유일한 지표이므로 대표 숫자로 살린다. KPI 카드로 떠 있을 때는 무엇의 양품률인지 맥락이 없었으나, 결과 블록 안으로 들어오면 맥락이 붙는다.

**(2) 누적 100% 바**

`ResultSummary`의 파이차트를 대체한다. 파이보다 폭을 덜 먹고 비교가 쉽다.

- 높이 1.4rem, 라운드 `0.4rem` (`--r-sm`)
- PASS · REJECT · FAIL 순서 고정. 순서를 바꾸지 않는다
- 합계가 `completed`와 항상 일치하므로 카드 3장 병렬이 아니라 누적 바가 맞다

**(3) 범례 3분할**

| 항목 | 내용 |
|---|---|
| 좌측 | 한글 라벨 + 영문 코드 (`정상 PASS`) |
| 우측 | 건수 + 비율 (`122` `95.3%`) |

**세 칸 모두 클릭 가능하다.** 클릭하면 완료 탭으로 이동하며 해당 그룹 필터가 적용된다(§8).

**(4) 탐지 카드 스트립** — §4.5

### 4.5 탐지 카드 스트립

F13·F14에 대한 답이다. `ResultSummary`의 검사 결과 테이블을 **대체한다** — 신설이 아니다.

기존 테이블을 대체하는 이유는 다음과 같다.

- 현행 테이블은 `Cell ID / Result / Time` 3열인데 **`Time` 열이 `-` 하드코딩**이다. WS 페이로드에 시각 필드가 없다.
- 나머지 두 열(`Cell ID`, `Result`)은 위 flow와 누적 바에서 이미 본 정보다.
- 블록 개수를 늘리지 않으면서 정보 가치를 올릴 수 있다. 신설하면 덩이가 하나 늘어 F1과 F14가 서로 싸운다.

#### 4.5.1 카드 내용

가장 최근 완료된 셀 **4~6개**를 가로로 나열한다.

| 요소 | 내용 |
|---|---|
| 썸네일 | CT 또는 RGB 이미지, bbox 오버레이 |
| 타입 배지 | `CT` / `RGB` |
| 판정 배지 | `PASS` / `REJECT` / `FAIL`, 상태색 적용 |
| 결함 유형 | `갈라짐` 등 `defectType` |
| 신뢰도 | `신뢰도 87%` |

카드 클릭 시 해당 셀의 배터리 상세(`/battery/:batteryCellId`)로 이동한다.

#### 4.5.2 배터리 상세 화면의 대응 변경

같은 이유로 `ImageBboxGrid`의 썸네일에도 판정 배지와 신뢰도를 직접 표기한다. 현재는 모달을 열어야만 보인다(§1.8).

모달(`ImageBboxModal`)의 `infoItems`는 그대로 유지한다. 썸네일에는 대표 결함 1건의 요약만, 모달에는 전체 목록을 둔다.

### 4.6 세로 예산

기준 뷰포트 `1920 × 920`에서 한 화면에 들어간다.

| 블록 | 높이 |
|---|---|
| 탭바 | 42.9px |
| 헤더 | 40px |
| flow 레인 | 200px |
| 결과 블록 | 320px |
| 여백 합 | 60px |
| **합계** | **약 660px** |

**스크롤은 허용하되 기대하지 않는다.** 기준 해상도에서 한 화면에 들어가도록 설계하고, 더 낮은 화면 높이에서만 스크롤이 생기도록 `overflow-y: auto`를 열어둔다.

남는 약 240px은 **여백으로 둔다.** 블록을 키우거나 하나 더 넣지 않는다. 현재 화면이 답답한 원인이 밀도이므로 여백 자체가 해결책이다.

## 5. 세부 탭 4종

### 5.1 공통 골격

4개 탭이 **동일한 2단 골격**을 공유한다. 현행은 탭마다 뼈대가 달라 탭을 넘길 때마다 눈이 새로 적응해야 한다.

- **요약 바** (상단 고정) — 단계명 + 대표 수치 + 상태 배지 + 단계별 부가 지표
- **목록 영역** (내부 스크롤) — 단계별 내용

| 항목 | 값 |
|---|---|
| 좌우 패딩 | 2rem (전체탭과 동일) |
| 요약 바 높이 | 8rem |
| 목록 영역 | 나머지 전체, `overflow-y: auto` + `scrollbar-gutter: stable` |

**페이지 자체는 스크롤하지 않는다.** 목록이 길어져도 요약 바는 항상 보여야 한다. 스크롤로 요약이 사라지면 "지금 몇 개인지"라는 맥락을 잃는다.

요약 바는 전체탭 flow 노드 카드가 가로로 늘어난 형태로 읽히도록 같은 슬롯 어휘(상태 점 · 단계명 · 영문 코드 · 대표 수치 · 단위)를 쓴다.

### 5.2 대기 탭

| 영역 | 내용 |
|---|---|
| 요약 바 | 대기 셀 수 · `/ 총 240` · 다음 배치 번호 |
| 목록 | 배치별 접이식 그룹. 배치 헤더(배치 번호 + 셀 수 + 펼침 화살표) + 셀 아이콘 그리드 |
| 장식 | 컨베이어 애니메이션 (현행 유지) |

현행 `PendingPanel`의 배치 드릴다운 구조가 이미 충실하므로 골격과 상태색만 새 언어로 맞춘다.

### 5.3 촬영 탭

| 영역 | 내용 |
|---|---|
| 요약 바 | 현재 배치 셀 수 · 촬영 완료 수 · 촬영 속도 · 현재 배치 번호 |
| 목록 | 배치별 접이식 그룹 (대기 탭과 동일 형태) |
| 장식 | 스캐너 애니메이션 (현행 유지) |

셀 아이콘은 `CAPTURING`과 `CAPTURED`를 명도로 구분한다 — 진한 청록 `#13777C` / 흐린 청록 `#85C4C8`.

### 5.4 분석 탭

현행 `AnalyzePanel`은 84줄, 카드 한 장으로 4개 탭 중 가장 빈약하다. 표시하는 실질 정보가 `Cell ID` 하나뿐이다(`Retry Count`는 WS가 아직 내려주지 않아 항상 `0`).

공통 골격을 적용하면서 비어 있던 목록 영역을 채운다.

| 영역 | 내용 |
|---|---|
| 요약 바 | 분석 중 셀 ID · 소속 배치 · 모델명(`YOLOv11-seg`) |
| 목록 | **분석 대기열** — 촬영 완료(`CAPTURED`) 후 분석을 기다리는 셀 목록 + **현재 분석 중 셀 상세** |
| 장식 | 배터리 충전 SVG (현행 유지, 이 탭에서만) |

`Retry Count`는 WS 모델에 필드가 추가되기 전까지 표시하지 않는다. 항상 `0`인 숫자를 큰 자리에 두면 정보가 아니라 노이즈다. §12에 후속 과제로 기록한다.

### 5.5 완료 탭

**서브카드 3장 병렬 구조를 필터 1축으로 전환한다.**

| 영역 | 내용 |
|---|---|
| 요약 바 | 완료 총 수 · 양품률 · `전체` / `PASS` / `REJECT` / `FAIL` 필터 |
| 목록 | 선택된 필터에 해당하는 셀 리스트 |
| 장식 | 셀 삽입 애니메이션 (현행 `complete-cell-enter` 유지) |

필터 전환은 즉시 반영한다. 전체탭 결과 블록의 범례를 클릭해 진입하면 해당 필터가 이미 선택된 상태로 열린다(§8).

셀 리스트의 각 항목은 셀 ID + 판정 배지로 구성하고, 클릭 시 배터리 상세로 이동한다.

### 6.2 브랜드 격리 규칙

브랜드 블루 `#0C5795`(brand-700)와 그 램프 전 스텝은 **상태 표현에 일절 사용하지 않는다.**

| 색 | 허용 용도 |
|---|---|
| `#0C5795` (brand-700) | 사이드바 활성 탭(아이콘 + 라벨), 빈 상태 시뮬레이션 시작 CTA |
| `#236CAE` (brand-600) | CTA 호버 |
| `#054477` (brand-800) | CTA 프레스 |
| `#EEF6FE` (brand-50) | 사이드바 활성 탭 배경, 행 hover 배경 |

**2026-08-07 개정** — 브랜드가 레드 `#e60012`(사이드바 활성 `#d94730`)에서 블루 `#0C5795`로 전환되었다. 옛 사이드바 활성색은 페이지 배경 `#ededed` 위에서 대비 3.66으로 WCAG AA(4.5)에 미달했으며, 이 문제는 전환과 함께 해소되었다.

진행 PROCESS도 파랑 `#2563eb`에서 청록 `#13777C`로 이동했다. 종전 근거는 "브랜드가 레드이므로 REJECT·FAIL이 레드 계열이면 충돌한다. 진행을 파랑으로 새로 배정하고 REJECT를 주황으로 밀어 푼다"였는데, **브랜드가 블루가 되는 순간 그 근거가 사라지고 오히려 브랜드 블루와 진행 파랑이 같은 계열로 충돌한다.** 사이드바 활성 탭과 진행 중 노드가 한 화면에 있을 때 두 색이 모두 파랑이면 "이 파랑이 브랜드인가 상태인가"가 섞인다.

청록으로 이동한 뒤 색상각 이격은 브랜드 블루 ↔ PROCESS 50도, PROCESS ↔ PASS 53도로 모두 충분하다. 상세 근거는 `BRAND_COLOR.md` §5를 참고한다.

**미결** — REJECT `#d97706`과 FAIL `#dc2626`은 색상각이 31도밖에 떨어져 있지 않고 REJECT는 흰 배경 대비도 3.19로 AA에 미달한다(`BRAND_COLOR.md` §9). 대시보드에서는 둘이 누적 바의 서로 다른 구간이라 위치로도 구분되지만, 목록 화면에서는 인접 배치되어 문제가 크다. `LIST_REDESIGN.md` §6.3이 이중 부호화(형태 차이)로 대응하며, 대시보드에도 같은 규칙을 적용할 수 있다.

### 6.3 결함 유형 팔레트 분리

리포트 화면의 결함 유형 도넛(`defectColors.ts`)은 위 5색과 **반드시 분리 선언**한다. 결함 유형 색이 상태색을 재사용하면 "이 색이 판정인가 결함 종류인가"가 섞인다.

## 7. 모션 규칙

### 7.1 탭 전환

**전체탭을 슬라이드 트랙에서 제외한다.**

| 전환 | 모션 |
|---|---|
| 전체 → 세부 (어느 탭이든) | 슬라이드 없음. 크로스페이드 120~160ms |
| 세부 → 전체 | 동일 |
| 세부 ↔ 세부 (대기·촬영·분석·완료) | 가로 슬라이드 0.3s |

근거는 다음과 같다.

- 대기 → 촬영 → 분석 → 완료는 **실제 공정 순서**다. 슬라이드가 그 순서 감각을 강화한다.
- '전체'는 순서 밖의 개요다. 슬라이드 트랙에 끼우면 **전체가 공정의 0번째 단계처럼 읽힌다.** 의미가 틀린다.
- 전체탭만 세로 길이가 다르다(§4.6). 높이가 다른 패널을 같은 가로 트랙에 이어붙이면 슬라이드 중 화면이 출렁인다. 트랙에서 빼면 남는 4장은 높이가 같아 이 문제가 사라진다.

현행 `translateX(activeTab * -120rem)` 방식은 '전체'에서 '완료'로 갈 때 480rem을 훑고 지나간다. 중간 3개 패널이 스쳐 지나가면서 F2가 지적한 "넘어간다"는 물리 감각이 생긴다.

### 7.2 슬라이드 거리

세부 탭끼리는 **실제 칸 수만큼** 미끄러진다. 대기에서 완료로 가면 3칸이다.

- 지속 시간은 거리와 무관하게 **0.3s 고정**. 먼 거리일수록 빠르게 지나가 체류 시간이 늘지 않는다
- 오른쪽 방향 = 공정 진행 방향, 왼쪽 = 역방향

슬라이드를 남긴 목적이 공정 순서 감각이므로 1칸 고정으로 축약하지 않는다. "멀리 왔다"는 감각 자체가 정보다.

**폴백 조건** — 3칸 이동 시 중간 패널의 무거운 렌더(셀 그리드 수백 개)로 프레임 저하가 관측되면 1칸 고정으로 전환한다. 관측 후 판단할 사항이다.

### 7.3 데이터 기반 모션

움직이는 것은 **지금 실제로 진행 중인 것**으로 한정한다.

| 대상 | 모션 | 조건 |
|---|---|---|
| 커넥터 | `stroke-dashoffset` 0.85s 무한 | 다음 단계가 활성일 때만 |
| 활성 노드 상태 점 | opacity · scale 펄스 1.4s | 해당 단계 활성 |
| 촬영 진행바 | `captureSpeed`초 동안 0 → 100% | `batchId`가 바뀌면 재시작 |
| 셀 타일 | `CAPTURING` 타일만 opacity 1s | `CAPTURED`는 정지 |
| 숫자 | 현행 `useCountUp` 유지 | 420~600ms |
| 누적 바 | width 420ms ease-out | — |

### 7.4 장식 애니메이션

세부 탭에는 탭마다 전용 장식이 하나씩 있다. **탭당 1개까지 유지한다.**

| 탭 | 장식 |
|---|---|
| 대기 | 컨베이어 |
| 촬영 | 스캐너 |
| 분석 | 배터리 충전 SVG |
| 완료 | 셀 삽입 pop |

**전체탭에는 장식 애니메이션을 두지 않는다.** 데이터 기반 모션만 사용한다. 전체탭은 이미 §7.3의 모션이 4개 돌고 있어 장식을 더하면 상한을 넘는다. (`OverviewPanel` 폐기로 배터리 충전 SVG는 전체탭에서 자동으로 사라진다.)

### 7.5 모션 상한과 접근성

- 한 화면에 동시에 도는 무한 애니메이션은 **최대 4개**로 제한한다. 탭이 배타적이므로 세부 탭 장식과 전체탭 모션은 동시에 보이지 않아 이 상한을 깨지 않는다.
- `prefers-reduced-motion: reduce`에서는 펄스·스피너·흐름선을 모두 끄고, 타이밍 진행바는 100%로 고정한다.

### 7.6 DOM 삽입 애니메이션

완료 셀처럼 새 노드가 삽입될 때 자동 재생되어야 하는 요소는 수정자 클래스(`.--enter`) 방식을 쓰지 않고 해당 클래스에 직접 `animation`을 선언한다. `ARCHITECTURE.md`의 "CSS 애니메이션 정책"을 그대로 따른다.

## 8. 인터랙션

### 8.1 진입 경로

탭바를 통한 직접 이동은 그대로 유지하고, flow에서 들어가는 경로를 **추가**한다.

| 클릭 대상 | 이동 | 부가 동작 |
|---|---|---|
| flow 대기 노드 | 대기 탭 | — |
| flow 촬영 노드 | 촬영 탭 | — |
| flow 분석 노드 | 분석 탭 | — |
| 결과 범례 `정상 PASS` | 완료 탭 | PASS 필터 적용 |
| 결과 범례 `불량 REJECT` | 완료 탭 | REJECT 필터 적용 |
| 결과 범례 `검사 실패 FAIL` | 완료 탭 | FAIL 필터 적용 |
| 탐지 카드 | `/battery/:batteryCellId` | — |
| 완료 탭 셀 항목 | `/battery/:batteryCellId` | — |

F3("클릭했을 때 더보기, 다른 페이지로 넘어가도 상관없음")이 이 경로를 명시적으로 허용한다.

### 8.2 필터 전달 요구사항

완료 탭은 **진입 시 그룹 필터를 받을 수 있어야 한다.** 범례에 `REJECT 5`가 떠 있는 것을 눌렀는데 완료 탭이 전체 목록으로 열리면 맥락이 끊긴다.

전달 방법(라우트 파라미터, 쿼리스트링, 스토어 등)은 FE 담당자가 결정한다. 이 문서는 요구사항만 규정한다.

### 8.3 모달을 쓰지 않는 이유

세부 정보를 모달로 띄우지 않고 탭 이동으로 처리한다. 세부 탭이 이미 탭으로 존재하므로 모달을 겹칠 이유가 없고, 모달 안에서 다시 배터리 상세로 페이지 전환이 일어나면 뒤로가기 동작이 꼬인다.

예외 — 배터리 상세의 이미지 확대(`ImageBboxModal`)는 현행대로 모달을 유지한다. 이것은 화면 전환이 아니라 같은 정보의 확대이므로 성격이 다르다.

## 9. 상태 변형

레이아웃은 바뀌지 않고 배지와 본문 문구만 바뀌므로 SVG 시안으로 그리지 않고 표로 규정한다.

시뮬레이션 실행 상태와 `WsStatus`(idle / connecting / open / reconnecting / closed)는 서로 다른 축이다. 하나는 시뮬레이션이 돌고 있는지, 다른 하나는 소켓이 붙어 있는지를 가리킨다.

노션 Core §6.7이 정의한 `simulation_run.status`는 **`RUNNING` · `COMPLETED` · `STOPPED` 3값**이다. FE 전용 타입 `SimulationRunStatus`는 시뮬레이션이 시작되기 전을 나타내는 `idle`을 추가로 갖는다.

| 상태 | 전체탭 본문 | 배지 |
|---|---|---|
| `idle` (FE 전용) | flow 레인과 결과 블록 대신 빈 상태 안내 + 시작 CTA. 빈 노드 카드 3장을 남기지 않는다 | 회색 · 대기 |
| `RUNNING` | flow 레인 + 결과 블록 | 초록 · Live, 점 펄스 |
| `COMPLETED` | 레인은 남기되 활성 강조를 끄고, 상단에 완료 배너 + 최종 집계 고정 | 초록 · 완료 |
| **`STOPPED`** | 레인과 결과 블록을 **그 시점 값 그대로 남기고 활성 강조를 끈다.** 상단에 중단 배너 + `시뮬레이션 재시작` 액션 | 회색 · 중단됨 |
| WS `reconnecting` | 본문 유지, 값은 마지막 수신값으로 동결 | 주황 · 재연결 중 |
| WS `closed` | 본문 유지 + 흐림 처리 | 회색 · 연결 끊김 |

**`STOPPED`와 `COMPLETED`를 구분하는 이유** — 전자는 사용자가 `POST /sim/stop`으로 중단시킨 것이고 후자는 전 배치가 처리된 것이다. 완료 배너가 "전 배치 처리 완료"라고 말하는데 실제로는 중간에 끊긴 것이면 집계 숫자를 오독하게 된다. 중단 배너는 처리되지 않고 남은 셀 수를 함께 표시한다.

`STOPPED`에서 flow 레인을 비우지 않는 이유는 "어디까지 갔다가 멈췄는지"가 정보이기 때문이다. 대기 노드에 남은 셀 수가 곧 미처리량이다.

세부 탭 4종도 같은 규칙을 따른다. `idle`에서는 요약 바의 수치가 0이 되고 목록 영역에 빈 상태 문구를 표시한다.

빈 상태 CTA 버튼과 중단 상태의 재시작 액션은 §6.2에 따라 브랜드 블루 `#0C5795`를 쓴다.

## 10. 데이터 의존성

### 10.1 탐지 카드 조회 경로

탐지 카드(§4.5)에 필요한 값들의 보유 현황은 다음과 같다.

| 경로 | 이미지 URL | bbox | 판정 | 결함 유형 | 신뢰도 |
|---|---|---|---|---|---|
| WS `PROGRESS.completed[]` | 없음 | 없음 | 있음 | 없음 | 없음 |
| `GET /battery` 목록 | 없음 | 없음 | 있음 | 없음 | 없음 |
| **`GET /battery/:batteryCellId`** | **있음** | **있음** | **있음** | **있음** | **있음** |

**신규 API 계약 없이 구현할 수 있다.** 최근 완료 셀 4~6개에 대해 기존 `GET /battery/:batteryCellId`를 호출하면 필요한 값이 모두 나온다.

대가는 셀 개수만큼 요청이 발생하는 것(N+1)이다. 4~6개 상한이면 감당 범위로 판단하나, 실측 후 판단은 FE 담당자의 몫이다.

**폴백** — N+1 호출이 부담스럽다고 판단되면 축소판으로 내린다. 썸네일 + bbox + 판정 배지만 표시하고 결함 유형과 신뢰도를 생략한다.

**개선 경로 (BE 협의 시)** — WS `PROGRESS.completed[]`에 대표 이미지 URL·`defectType`·`confidence`를 추가하면 추가 조회 없이 채울 수 있다. 협의가 진행 중이므로 계약이 확정되면 이 경로로 전환한다. 화면 정의는 그대로 유지된다.

### 10.2 확정 불필요 항목

이 재설계는 아래 미확정 사항에 의존하지 않는다.

- `POST /dashboard` 응답 스키마 — 누적 통계 대시보드는 이번 범위에 없다(§12)
- `GET /sim/status` 세션 복구 — 이번 범위에 없다(§12)
- WS `report.ready` 이벤트 — 이번 범위에 없다
