# 규제준수 UI·기능 분석

## 1. 기준과 범위

|항목|내용|
|---|---|
|입력 문서|`웹사이트_개발_규제준수_가이드.md`|
|대상|CELLNEX 프론트엔드와 인증·인가 연동 계약|
|목표|필요한 페이지, 공통 UI 상태, 백엔드 통제를 분리한다|
|주의|화면 문구는 설계 초안이다. 운영기관명, 책임자, 연락처, 보유기간은 배포 전 확정해야 한다|

가이드의 `SHA-256 이상`은 단순 SHA-256 저장으로 구현하지 않는다. 빠른 일반 해시는 비밀번호 저장에 적합하지 않으므로 서버는 salt와 work factor를 포함하는 Argon2id를 우선 사용하고, 환경 제약이 있으면 scrypt·bcrypt·PBKDF2를 검토한다.

## 2. 필요한 페이지

|우선순위|화면|구분|이유|산출물|
|---|---|---|---|---|
|P0|회원가입|기존 화면 개편|수집 목적·항목·보유기간을 보여주고 명시적 필수 동의를 받아야 한다. 비밀번호 정책도 입력 중 확인 가능해야 한다|`assets/compliance/01-signup-consent.svg`|
|P0|개인정보처리방침|새 공개 페이지|로그인 여부와 무관하게 상시 접근 가능한 공개 문서와 변경 이력이 필요하다|`assets/compliance/02-privacy-policy.svg`|
|P1|보안·규제 UI 상태|공통 상태 시트|로그인 실패·잠금, 업로드 차단, 마스킹, 권한 거부를 화면별로 중복 설계하지 않기 위한 기준이다|`assets/compliance/03-security-states.svg`|
|P0|런타임 규제 통합|구현 검토 시트|공통 푸터, 마스킹, 관리자 라우트와 CSRF 계약을 실제 화면 흐름으로 함께 검토한다|`assets/compliance/04-runtime-compliance.svg`|

`개인정보처리방침`은 `/privacy` 같은 공개 라우트로 두고 `PrivateRoute` 바깥에서 접근시킨다. 로그인·회원가입과 전체 서비스 푸터의 `개인정보처리방침` 링크가 같은 라우트를 가리켜야 한다.

## 3. 기존 화면에 추가할 기능

|영역|필수 변경|프론트엔드 책임|서버 책임|
|---|---|---|---|
|회원가입 동의|목적·항목·보유기간, 거부권과 불이익, 필수 동의|개별 체크박스, 전문 보기, 미동의 시 제출 차단|동의 버전·시각·사용자 기록 보관|
|비밀번호|정책 안내와 입력 검증|실시간 조건 표시, 확인값 일치 검사|Argon2id 등 적응형 해시와 고유 salt, 공통·유출 비밀번호 방어|
|로그인 보호|반복 실패 대응|일반화된 오류, 남은 시도 또는 잠금 상태, CAPTCHA 슬롯|시도 횟수·잠금·rate limit의 서버 판정|
|개인정보 노출|이름·연락처·이메일 마스킹|표시 컴포넌트의 일관된 마스킹|권한별 원문 반환 제한, 감사 로그|
|전체 푸터|처리방침 상시 링크|공개·인증 레이아웃에 동일 링크|정책 버전과 시행일 제공|
|파일 업로드|허용 형식·크기·개수와 거부 사유|선제 검증과 접근 가능한 오류|MIME·시그니처 재검증, 난수 파일명, 저장 경로 격리|
|상태 변경 요청|CSRF 방어|서버 방식에 따라 토큰 헤더 또는 쿠키 연동|토큰·SameSite 정책 검증|
|관리자 접근|권한 거부 상태|메뉴 숨김은 보조 수단, 403 표시|모든 엔드포인트에서 세션 기반 인가|
|리다이렉트|외부 URL 제한|앱 내부 상대경로 우선 사용|허용 도메인·경로 검증|

## 4. FE 구현 결과와 남은 서버 의존성

|항목|FE 상태|최종 준수 조건|
|---|---|---|
|회원가입 동의·비밀번호 검사|구현|BE가 `privacyConsent`, `privacyPolicyVersion`을 검증하고 동의 이력을 저장해야 함|
|개인정보처리방침 공개 라우트|`/privacy` 구현|운영 배포 환경에 실제 책임자·이메일·전화번호를 설정해야 함|
|전체 화면 처리방침 링크|인증·서비스 레이아웃 구현|새 레이아웃 추가 시 `LegalFooter` 재사용|
|CSRF 클라이언트 계약|`GET /auth/csrf`, `XSRF-TOKEN`, `X-XSRF-TOKEN` 연동 준비|BE가 토큰을 발급하고 상태 변경 요청에서 검증해야 함|
|개인정보 마스킹|공지 작성자 이름·이메일에 적용|BE가 일반 응답에서 원문을 제거하고 권한별 DTO를 분리해야 함|
|관리자 UX 가드|작성·수정 라우트와 버튼에 적용|BE가 JWT 역할을 복원하고 모든 관리자 API에서 403을 강제해야 함|
|파일 업로드 UI 없음|현재 비적용|업로드 도입 시 공통 검증기를 먼저 적용|

## 5. 구현 순서

1. BE가 동의 이력·CSRF·JWT 권한 복원을 구현한다.
2. FE와 BE 통합 테스트로 동의 누락, CSRF 누락, 일반 사용자 관리자 접근이 모두 거부되는지 확인한다.
3. 운영 주체가 개인정보 보호책임자 이름·이메일·전화번호를 배포 환경에 설정한다.
4. 개인정보 원문이 일반 API와 로그에서 제거됐는지 점검한다.
5. 업로드 기능 도입 시 확장자·MIME·시그니처 서버 화이트리스트를 함께 구현한다.

## 6. 참고 기준

- 개인정보 보호법 시행령 제17조: 동의는 자유롭고 구체적·명확하며 쉽게 읽을 수 있어야 하고, 동의 여부를 명확히 표시할 수 있어야 한다.
- 개인정보 포털의 동의 예시는 필수 항목, 수집 목적, 보유기간을 분리해 제시한다.
- 개인정보 처리방침 작성지침(2025.4.)을 기준으로 최종 정책 문구와 공개 항목을 법무·개인정보 담당자가 검토해야 한다.
- OWASP Password Storage Cheat Sheet: 단순 SHA-256 대신 salt와 work factor를 갖는 적응형 비밀번호 해시를 사용한다.
