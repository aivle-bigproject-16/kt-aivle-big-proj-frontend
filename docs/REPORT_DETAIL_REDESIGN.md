## 0. 배경

### 0.1 LLM 템플릿이 화면으로 샌다

동료가 작업 중인 개별 리포트 상세 화면에서 아래 텍스트가 그대로 렌더링됐다.

```
분석 코멘트: [결함의 위치적 데이터를 사용해 결함의 위치적 특성
             (군집형/분산형, 특정 좌표계 편중 여부)과 내·외부 결함의 연관성
             1~2 줄로 핵심만 간단히 요약]

[결함타입명]: 0 건
[결함타입명]: 0 건

분석 코멘트: [현재 셀의 불량 양상에 대한 짧은 요약.]
```

LLM 프롬프트 템플릿의 대괄호 placeholder가 사용자에게 노출된 상태다.

### 0.2 원인 — 구조화 필드가 아니라 텍스트를 파싱하고 있다

화면의 우측 4개 섹션(셀 기본 정보 · 결함의 위치적 특성 · 검사 요약 및 이미지 타입별 현황 · 주요 결함 유형 분석)은 **`content` 마크다운 문자열을 정규식으로 쪼개 만든 것**이다. 구조화된 응답 필드를 읽는 것이 아니다.

| 화면 항목 | 실제 출처 | 안정성 |
|---|---|---|
| `Cell Serial No` | `cellSerialNo` 필드 | 안정 |
| `Inspection ID` | **필드 없음.** `IndividualReportDetail`에 `inspectionId`가 존재하지 않는다 | content 파싱 |
| 총 검사 이미지 수 | `ctImages.length + rgbImages.length`로 계산 가능하나 파싱값 사용 | content 파싱 |
| 결함의 위치적 특성 | content 파싱 | 불안정 |
| 결함 유형별 건수 | **필드 없음.** Core §10.5 — 개별 리포트 조회에 결함 유형·confidence가 없다. `imageMappings[]`는 bbox 좌표만 | content 파싱 |

LLM이 템플릿을 채우지 못하면 대괄호가 새고, 파싱 규칙이 어긋나면 섹션이 통째로 비거나 엉뚱한 값이 들어간다. Core §6.8이 리포트 실패 사유에 `MALFORMED_RESPONSE`(마크다운 템플릿 파괴)를 따로 둔 것도 이 취약성 때문이다.

### 0.3 일일 리포트는 구조화되어 있다

같은 성격의 숫자를 일일 리포트는 필드에서 직접 읽는다.

```ts
summary: {
  totalCount: number
  passCount: number
  rejectCount: number
  failedCount: number
  defects: { defectType: string; count: number }[]
}
```

**개별과 일일이 같은 정보를 서로 다른 신뢰도로 얻고 있다.** 개별은 텍스트에서 긁고, 일일은 필드에서 읽는다.

### 0.4 쓰이지 않는 구조화 데이터가 이미 있다

개별 리포트에는 `GET /reports/individual/:reportId/cell-view`가 반환하는 `CellDefectView`가 있고, 그 안에 파싱 없이 그릴 수 있는 값이 이미 들어 있다.

```ts
cloud.metrics: { dvfPpm: number; posSliceRate: number; defectCount: number }
annotation: {
  pattern: 'LOCAL_CLUSTER' | 'AXIAL_PENETRATING' | 'VOLUMETRIC' | 'NONE'
  severity: 'HIGH' | 'MEDIUM' | 'LOW'
  highlights: { zone: string; note: string }[]
  caption: string
  citedMetrics: string[]
}
```

현행 `Cell3DView`가 `metrics` 3종과 `highlights`·`caption`을 이미 쓰고 있으나, 3D 캔버스 하단에 작게 붙어 있어 존재감이 없다. `pattern`은 아예 화면에 안 나온다.

## 1. 재설계 원칙

`DASHBOARD_REDESIGN.md` §2를 승계한다. 이 화면에 적용할 때의 해석은 다음과 같다.

### 1.1 구조화 필드와 생성 텍스트를 분리한다

**이 문서의 핵심 원칙이다.**

| 구분 | 출처 | 표현 |
|---|---|---|
| **사실** | 응답의 구조화 필드 | 카드·수치·배지·차트 |
| **서술** | LLM이 생성한 `content` | **원문 그대로** 단일 본문 블록 |

`content`를 파싱하지 않는다. LLM이 무엇을 어떤 형식으로 썼든 화면이 깨지지 않는다. 서술은 서술로 읽히면 된다.

이 분리는 시각적으로도 드러나야 한다. 사실 영역과 서술 영역이 같은 카드 안에 섞이면 사용자가 어느 숫자가 검증된 값인지 구별할 수 없다.

### 1.2 값이 없으면 없다고 말한다

`0건`과 `데이터 없음`은 다른 상태다. 개별 리포트는 **REJECT 또는 FAIL 검사에만 생성되므로**(Core §4.8) 결함이 0건인 리포트는 원칙적으로 존재하지 않는다. 0이 표시된다면 그것은 정상값이 아니라 데이터 결손 신호다.

| 상황 | 표현 |
|---|---|
| 필드가 `null`이거나 배열이 비었다 | `데이터 없음` — 뉴트럴 회색 |
| 계약상 존재해야 하는데 0이다 | `확인 필요` — REJECT 주황 + 사유 문구 |
| 실제로 0인 것이 정상이다 | `0` — 일반 수치 표기 |

### 1.3 껍데기를 통일한다

개별 상세와 일일 상세가 같은 골격을 공유한다. 목록에서 타입 토글로 오가는 구조이므로(`LIST_REDESIGN.md` §5.2) 상세 화면끼리도 형태가 일치해야 한다.

### 1.4 디자인 언어

`DASHBOARD_REDESIGN.md` §2.6을 그대로 따른다. 카드 배경 `#ffffff`, 바닥 `#ededed`, 테두리 없음, 그림자 `0 2px 8px rgba(0,0,0,0.25)`. 라운드는 §2.7의 5단계 스케일(상한 15px)을 따른다.

**3D 뷰 캔버스만 예외로 어두운 배경을 쓴다.** 점군을 배경과 분리하려면 대비가 필요하다. 다만 카드 자체는 흰색이고 캔버스 영역만 어둡다 — 현행처럼 카드 전체를 검게 만들지 않는다.

## 2. 공통 골격

### 2.1 5슬롯

- **1 뒤로가기** — `← 개별 리포트 목록으로` / `← 일일 리포트 목록으로`
- **2 리포트 헤더** — 제목 · 식별자 · 상태 배지 · 생성/수정 일시
- **3 사실 영역** — 구조화 필드로 그린 카드들
- **4 서술 영역** — LLM `content` 원문 블록
- **5 이미지 영역** — CT/RGB 이미지 + bbox 오버레이

슬롯 3·4·5의 배치는 화면별로 다르지만 슬롯의 존재와 순서는 동일하다.

### 2.2 페이지 컨테이너

`LIST_REDESIGN.md` §3.2와 동일하다.

| 항목 | 값 |
|---|---|
| 좌우 패딩 | `2rem` (20px) |
| 콘텐츠 가용 폭 | `116rem` (1160px) |
| 배경 | 전역 `--bg` 상속 |

### 2.3 리포트 헤더

| 슬롯 | 개별 | 일일 |
|---|---|---|
| 제목 | `title` (`null`이면 `개별 리포트 #{reportId}`) | `title` (`null`이면 `일일 리포트 #{reportId}`) |
| 좌측 배지 | `cellSerialNo` (뉴트럴) | `reportDate` (뉴트럴) |
| 우측 식별자 | `RPT-{reportId}` mono | 동일 |
| 상태 배지 | `status` (§5) | 동일 |
| 메타 | 생성일시 · 수정일시 | 생성일시 · 수정일시 |

`BatteryInfoHeader`(`shared/ui`)가 이 구조를 이미 갖고 있다. 상태 배지 슬롯만 추가하면 두 화면이 공유할 수 있다.

### 2.4 서술 영역 규격

| 항목 | 값 |
|---|---|
| 제목 | 개별 = `AI 분석 소견`, 일일 = `일일 총평` |
| 부제 | `LLM 생성` 배지 (뉴트럴, mono) |
| 본문 | `content` 원문. 마크다운이면 렌더, 아니면 `white-space: pre-wrap` |
| 최대 폭 | `68ch` — 긴 줄은 읽기 어렵다 |
| 비었을 때 | `본문이 없습니다` |

**`LLM 생성` 배지를 두는 이유** — 이 블록만 검증되지 않은 텍스트임을 사용자가 알아야 한다. 사실 영역의 숫자와 같은 위계로 읽히면 안 된다.

## 3. 개별 리포트 상세

### 3.1 레이아웃

세로 2단, 각 단은 좌우 2열이다.

- **상단** — 좌: 3D 결함 뷰 (`72rem`) / 우: 결함 지표 카드 (`42rem`)
- **하단** — 좌: CT·RGB 이미지 (`72rem`) / 우: AI 분석 소견 (`42rem`)

좌열 `720px` + gap `20px` + 우열 `420px` = `1160px`으로 가용 폭에 정확히 맞는다.

### 3.2 사실 영역 — 결함 지표 카드

`CellDefectView`의 구조화 필드만 쓴다. content 파싱 없음.

| 항목 | 필드 | 표현 |
|---|---|---|
| 위험도 | `annotation.severity` | 배지. HIGH=`#dc2626` / MEDIUM=`#d97706` / LOW=`#1e7e34` |
| 결함 패턴 | `annotation.pattern` | 배지. 아래 라벨 표 참조 |
| DVF | `cloud.metrics.dvfPpm` | 큰 수치 + `ppm` |
| 결함 수 | `cloud.metrics.defectCount` | 큰 수치 + `개` |
| 양성 슬라이스율 | `cloud.metrics.posSliceRate` | 큰 수치 + `%` (× 100, 소수 1자리) |
| 주요 구역 | `annotation.highlights[]` | `zone` + `note` 목록 |
| 캡션 | `annotation.caption` | 지표 카드 하단 1~2줄 |

**결함 패턴 라벨**

| 코드 | 한글 |
|---|---|
| `LOCAL_CLUSTER` | 국부 군집형 |
| `AXIAL_PENETRATING` | 축 관통형 |
| `VOLUMETRIC` | 체적 분산형 |
| `NONE` | 패턴 없음 |

`annotation`이 `null`이면 위험도·패턴·구역·캡션을 숨기고 지표 3종만 표시한다. 빈 배지를 남기지 않는다.

### 3.3 3D 결함 뷰

현행 `Cell3DView`의 데이터 처리는 유지하고 껍데기만 바꾼다.

| 항목 | 현행 | 변경 후 |
|---|---|---|
| 카드 배경 | 검정 카드 전체 | **흰 카드 + 캔버스 영역만 어둡게** (`#1b2027`) |
| 테두리 | `severity` 색 테두리 | 제거. 위험도는 지표 카드의 배지가 담당 |
| 지표 3종 | 캔버스 하단에 작게 | **지표 카드로 이동**(§3.2). 캔버스는 시각화에 집중 |
| 캡션·구역 | 카드 하단 | 지표 카드로 이동 |
| 위험도 배지 | 카드 헤더 | 지표 카드 상단 |

중복을 없애는 것이 목적이다. 현행은 같은 수치가 3D 카드에도, 파싱된 우측 섹션에도 나온다.

캔버스 헤더에는 `셀 3D 결함 뷰` 제목과 `{cellId}` 식별자, 그리고 조작 힌트(`드래그로 회전 · 휠로 확대`)만 둔다.

점군 색은 `area`(신뢰도) 임계로 3단계다. 현행 값(`#e34948` / `#eda100` / `#1baf7a`)을 **상태 5색으로 통일한다** — `#dc2626` / `#d97706` / `#1e7e34`.

### 3.4 이미지 영역

CT와 RGB를 하나의 카드 안에 타입 탭으로 나눈다. 현행은 카드 2장이라 한쪽이 비면 빈 카드가 그대로 남는다.

| 항목 | 값 |
|---|---|
| 탭 | `CT ({n})` / `RGB ({n})` — 건수 표기 |
| 썸네일 | bbox 오버레이. 클릭 시 `ImageBboxModal` |
| bbox 색 | REJECT 주황 `#d97706` |
| 비었을 때 | 해당 탭에 `이미지가 없습니다` |
| 양쪽 다 비었을 때 | 카드 전체를 빈 상태로. §1.2에 따라 **`확인 필요`** 표기 |

**bbox 좌표 목록을 화면에 노출하지 않는다.** 현행은 `x: 12, y: 34, w: 56, h: 78` 형태의 목록을 우측에 나열하는데, 좌표 숫자는 사용자에게 의미가 없다. 이미지 위 오버레이가 같은 정보를 이미 보여준다. 좌표는 모달에서만 보조로 표시한다.

### 3.5 결함 유형이 없다는 사실을 숨기지 않는다

Core §10.5가 등재한 대로 개별 리포트 조회에는 **결함 유형과 confidence가 없다.** FR-DETAIL-004(“confidence, bbox 좌표, AI 원본 응답 확인”, Must)가 미충족이다.

현행 화면은 이것을 content 파싱으로 메우려다 `[결함타입명]: 0 건`을 노출했다. 재설계에서는 **해당 카드를 만들지 않는다.** 없는 데이터를 있는 것처럼 그리지 않는다.

대신 §7에 협의 대상으로 기록하고, 데이터가 붙으면 지표 카드 아래에 결함 유형 분포를 추가한다. 자리는 비워둔다.

## 4. 일일 리포트 상세

### 4.1 레이아웃

세로 3단이다.

- **상단** — KPI 4장 가로 (`1160px`)
- **중단** — 좌: 결함 유형 분포 (`72rem`) / 우: 참조 이미지 (`42rem`)
- **하단** — 일일 총평 (`1160px`)

### 4.2 사실 영역 — KPI 4장

`summary` 필드를 직접 읽는다. 파싱 없음.

| 카드 | 값 | 색 |
|---|---|---|
| 총 검사 수 | `totalCount` | 뉴트럴 |
| 정상 | `passCount` + 비율 | PASS `#1e7e34` |
| 불량 | `rejectCount` + 비율 | REJECT `#d97706` |
| 검사 실패 | `failedCount` + 비율 | FAIL `#dc2626` |

비율은 `totalCount` 대비 백분율이며 소수 1자리다. `totalCount`가 0이면 비율을 `-`로 표기한다.

현행은 `총 검사 수량`과 `종합 불량률` 2장만 쓰고 `passCount`·`failedCount`를 버린다. 4장으로 늘리면 대시보드 결과 블록의 범례 3분할과 어휘가 맞는다.

### 4.3 결함 유형 분포

`summary.defects[]`(`{ defectType, count }`)를 쓴다.

| 항목 | 값 |
|---|---|
| 형태 | 가로 막대 목록 (도넛 아님) |
| 정렬 | `count` 내림차순 |
| 라벨 | 영문 코드를 한글로 변환 (아래 표) |
| 색 | **결함 유형 전용 팔레트** — 상태 5색·브랜드 램프와 분리 |

**결함 유형 라벨** (Core §6.5)

| 코드 | 한글 | 비고 |
|---|---|---|
| `CRACK` | 갈라짐 | RGB 모델 출력 |
| `SPOT` | 오점 | RGB 모델 출력 |
| `MICRO_DEFECT` | 미세결함 | CT 모델 출력 |
| `SWELLING` | 부풀음 | **출력하는 모델이 없어 항상 0** |

`SWELLING`은 값이 0이면 목록에서 제외한다. 코드표에는 있으나 이를 출력하는 모델이 없다.

**도넛에서 가로 막대로 바꾸는 이유** — 항목이 3종뿐이고 값 차이가 크다. 도넛은 작은 조각의 비교가 어렵고 라벨을 바깥에 붙여야 해서 폭을 많이 먹는다. 가로 막대는 값을 직접 읽을 수 있고 항목이 늘어도 세로로 확장된다.

### 4.4 참조 이미지

`ctImageUrl` 또는 `rgbImageUrl` 중 하나다. Core §10.5(B-7)에 따르면 이 이미지는 **그날 REJECT 검사 중 첫 번째 이미지**다.

이 사실을 캡션에 명시한다 — `{TYPE} · 당일 첫 REJECT 검사 이미지`. 현행 캡션은 `CT 이미지`뿐이라 이 이미지가 왜 대표인지 알 수 없다.

### 4.5 실패 사유 라벨

현행 `FAILURE_REASON_LABEL`이 **잘못된 값 집합을 쓰고 있다.**

| 현행 코드 | 문제 |
|---|---|
| `INCOMPLETE_SET` | **폐기 확정**(Core B-10). 존재하지 않는 값 |
| `PARTIAL_ANALYSIS_FAILURE` | **폐기 확정**(Core B-10) |
| `AI_SERVER_ERROR` · `TIMEOUT` | **AI 실패 사유**다. 리포트 실패 사유가 아니다 |

리포트 실패 사유는 Core §6.8의 **별도 5값**이다. 두 집합을 섞지 않는다.

| 값 | 사용자 문구 |
|---|---|
| `VLM_TIMEOUT` | 리포트 생성 시간이 초과되었습니다 |
| `VLM_UNREACHABLE` | 리포트 생성 서버에 연결할 수 없습니다 |
| `VLM_SERVER_ERROR` | 리포트 생성 중 서버 오류가 발생했습니다 |
| `IMAGE_LOAD_FAILED` | 참조 이미지를 읽지 못했습니다 |
| `MALFORMED_RESPONSE` | 리포트 형식이 올바르지 않습니다 |

## 5. 상태 변형

`status`는 `PENDING` · `COMPLETED` · `FAILED` 3값이다(Core §6.6).

| 상태 | 화면 | 배지 |
|---|---|---|
| `PENDING` | 헤더만 표시. 본문 자리에 진행 안내 + 스피너 + **`새로고침`** 버튼 | `#13777C` / `#EBF8F9` |
| `COMPLETED` | 전체 표시 | `#5b5f63` 뉴트럴, 배경 없음 |
| `FAILED` | 헤더만 표시. 본문 자리에 실패 사유(§4.5) + **`재생성`** 버튼 | `#dc2626` 테두리 배지 + 삼각 마커 |

색과 형태 규칙은 `LIST_REDESIGN.md` §6.2·§6.3을 그대로 따른다.

**`PENDING`에 새로고침 버튼을 두는 이유** — 완료 시점을 알리는 WS `report.ready` 이벤트가 API_SPEC에 확정되어 있지 않고 FE도 구독하지 않는다. 자동 갱신 수단이 없으므로 수동 재조회 수단이 있어야 한다.

**`FAILED`에 재생성 버튼을 두는 이유** — FR-REPORT-008("디스패치 후 미완료 리포트 재시도", Should)에 대응한다. `POST /reports/*`에 `forceRegenerate` 플래그가 이미 정의되어 있다.

### 5.1 로딩·에러

| 상황 | 처리 |
|---|---|
| 조회 중 | 헤더·카드 골격을 스켈레톤으로. `LIST_REDESIGN.md` §7.1과 동일 규격 |
| 조회 실패 | 에러 블록 + `다시 시도` 버튼 |
| 3D 뷰만 실패 | 해당 카드에만 에러 표시. 나머지 화면은 정상 렌더 |

3D 뷰는 별도 엔드포인트(`/cell-view`)라 독립적으로 실패할 수 있다. 한 카드의 실패가 화면 전체를 막지 않는다.
