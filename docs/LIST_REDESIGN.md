### 0.2 Core SSOT 대조 결과

설계 전 노션 Core(시스템 계약서, 2026-08-03 기준)와 API 명세서 DB를 대조했다. 코드와 어긋나는 지점이 다음과 같다.

| 항목 | 코드 현행 | Core 기준 |
|---|---|---|
| `cellType` | `POUCH` · `CYLINDRICAL` · `PRISMATIC` 3종 | **2종.** `PRISMATIC`은 존재하지 않는 셀 타입 — 명세서·FE 타입에서 제거 대상 (§10.3) |
| `FailureReason` | 5값 | **3값.** `TIMEOUT` · `AI_SERVER_ERROR` · `MALFORMED_RESPONSE`. `INCOMPLETE_SET`·`PARTIAL_ANALYSIS_FAILURE`는 폐기 확정 (B-10) |
| 리포트 실패 사유 | 정의 없음 | AI 실패와 **별도 5값** (`VLM_TIMEOUT` · `VLM_UNREACHABLE` · `VLM_SERVER_ERROR` · `IMAGE_LOAD_FAILED` · `MALFORMED_RESPONSE`). 두 집합을 섞지 않는다 (§6.8) |
| 결함 유형 | 4종 코드표 | 코드는 4종이나 **실제 모델 출력은 3종.** CT=`MICRO_DEFECT`, RGB=`CRACK`·`SPOT`. `SWELLING`을 출력하는 모델이 없어 통계에서 항상 0 (§6.5) |

API 명세서 DB에서 확인한 파라미터는 다음과 같다. 세 엔드포인트 모두 BE 구현 상태가 **"진행 중"**이다.

| 엔드포인트 | 파라미터 |
|---|---|
| `GET /battery` | `page` · `size` |
| `GET /reports/individual` | `page` · `size` · **`sort`** |
| `GET /reports/daily` | `page` · `size` · **`sort`** |

정렬은 리포트 목록에만 가능하다. 배터리 목록에는 `sort`가 없다.

## 1. 현행 요소 분해

### 1.1 라우트 구조

| 라우트 | 페이지 | 컴포넌트 |
|---|---|---|
| `/battery` | `BatteryPage` | `BatteryList` |
| `/reports/individual` | `IndividualReportPage` | `IndividualReportTable` + `ReportTypeToggle` |
| `/reports/daily` | `DailyReportPage` | `DailyReportTable` + `ReportTypeToggle` |

사이드바는 "리포트 목록" 탭 하나로 `/reports/daily`를 가리키고 `matchPrefix="/reports"`로 두 라우트를 같은 탭으로 취급한다. 정보구조상 이미 하나인데 라우트만 둘로 갈려 있다.

### 1.2 골격 불일치

| 화면 | 헤더 | 툴바 | 본문 | 푸터 |
|---|---|---|---|---|
| 배터리 목록 | 타이틀 + 영문 부제 + `Export CSV` `+ New Query` | 탭 3개 + 날짜 필터 | 테이블 카드 | 건수 + 페이지네이션 |
| 일일 리포트 | 타이틀 + 영문 부제 + `ReportTypeToggle` | 없음 | 테이블 카드 | 동일 |
| 개별 리포트 | 타이틀 + 영문 부제 + `ReportTypeToggle` | 없음 | 테이블 카드 | 동일 |

배터리만 툴바 행이 있고, 액션 자리에 들어가는 것도 셋 다 다르다.

### 1.3 페이지 컨테이너가 인라인 스타일이다

```tsx
// IndividualReportPage.tsx · DailyReportPage.tsx
<div style={{ padding: 24, fontFamily: 'sans-serif', background: '#F8F9FA', minHeight: '100%' }}>
```

세 가지 문제가 겹쳐 있다.

- `padding: 24`가 **px 고정**이라 rem 스케일링을 타지 않는다. 대시보드는 `2rem`으로 확정돼 있어 좌우 정렬이 어긋난다.
- `fontFamily: 'sans-serif'`가 박혀 있어 이 화면만 Inter를 쓰지 않는다.
- `background: '#F8F9FA'`가 전역 `--bg: #ededed`와 다른 값이다.

### 1.4 두 리포트 테이블이 복붙이다

`DailyReportTable.tsx`와 `IndividualReportTable.tsx`는 `PAGE_SIZE` · `STATUS_LABEL` · `formatDateTime` · 페이징 계산 · 푸터 · 테이블 구조가 전부 중복이다. 복사 흔적이 **유령 컬럼**으로 남아 있다.

```tsx
// IndividualReportTable.tsx
<th>상태</th><th>제목</th><th></th><th>생성일시</th><th>상세</th>
...
<td>{item.title ?? ...}</td><td></td><td>{formatDateTime(item.createdAt)}</td>
```

일일 쪽 `판정일자` 컬럼 자리를 빈 `<th></th>` / `<td></td>`로 남겨둔 것이다.

### 1.5 페이지네이션이 이중이고 서로 싸운다

```ts
// BatteryList.tsx
useEffect(() => { fetchList() }, [fetchList])          // page·size 둘 다 undefined
const filteredList = list.filter(...)                   // 로드된 것 안에서만 필터
const totalPages = Math.ceil(filteredList.length / 20)  // pageable 무시하고 재계산
```

스토어는 `pageable`(`totalElements` · `totalPages`)을 받아 저장하지만 **컴포넌트가 사용하지 않는다.** 리포트는 `fetchList(0, 100)`으로 100개를 고정 요청하고 클라이언트에서 20개씩 자른다 — **101번째 리포트는 접근할 방법이 없다.**

그 결과 두 가지 거짓말이 발생한다.

- 배터리 목록의 "불량 이력" 탭은 전체 불량이 아니라 **로드된 것 중의 불량**이다.
- 푸터의 `Showing 1 to 20 of 47 entries`에서 `47`은 총계가 아니라 **받아온 배열 길이**다.

### 1.6 죽은 버튼

`Export CSV`와 `+ New Query` 버튼에 `onClick` 핸들러가 없다. 날짜 필터 `2024-05-12 - Today`도 하드코딩이고 핸들러가 없다.

### 1.7 리포트 생성 진입점이 없다

`create` 액션은 두 상세 스토어에 구현되어 있다.

- `useDailyReportDetailStore.actions.create`
- `useIndividualReportDetailStore.actions.create`

그런데 **이 액션을 호출하는 컴포넌트가 하나도 없다.** 현재 FE에서는 `POST /reports/daily` · `POST /reports/individual`을 호출할 방법이 없다. FR-REPORT-001·003이 Must인데 진입점이 존재하지 않는다.

### 1.8 중복 어포던스

세 테이블 모두 행 전체가 클릭 가능한데(`onClick` + `cursor: pointer`) 맨 오른쪽에 `상세` 컬럼의 chevron 버튼이 또 있다. 같은 목적지로 가는 진입점이 한 행에 두 개다.

## 2. 재설계 원칙

`DASHBOARD_REDESIGN.md` §2를 승계한다. 목록 화면에 적용할 때의 해석은 다음과 같다.

### 2.1 껍데기를 통일하고 내용물만 차등한다

세 목록이 4슬롯 골격을 공유한다. 슬롯의 위치·높이·정렬은 고정이고, 채워지는 값만 화면별로 다르다. 사이드바에서 배터리 목록 ↔ 리포트 목록을 오갈 때 헤더 높이와 액션 위치가 튀지 않아야 한다.

### 2.2 한 정보는 한 화면에 한 번만 그린다

행 클릭과 `상세` 버튼처럼 같은 목적지로 가는 진입점을 둘 두지 않는다.

### 2.3 화면이 데이터의 한계를 숨기지 않는다

서버 필터·서버 페이지네이션이 없는 상태에서 총계처럼 보이는 표기를 쓰지 않는다. 로드분 기준임이 문구에서 드러나야 한다.

### 2.4 색에만 의존하지 않는다

판정 배지는 색과 형태를 함께 쓴다. 근거는 §6.3.

### 2.5 디자인 언어

`DASHBOARD_REDESIGN.md` §2.6을 그대로 따른다.

| 항목 | 값 |
|---|---|
| 카드 배경 | `#ffffff` |
| 페이지 배경 | `#ededed` (`--bg`) |
| 테두리 | 사용하지 않음 |
| 라운드 | **5단계 스케일, 상한 15px** — `DASHBOARD_REDESIGN.md` §2.7 |
| 그림자 | `0 2px 8px rgba(0, 0, 0, 0.25)` (px 고정) |
| 본문 텍스트 | `#191c1d` |
| 보조 텍스트 | `#5b5f63` |

## 3. 공통 골격

### 3.1 4슬롯

- **1 페이지 헤더** — 타이틀 + 우측 액션
- **2 툴바** — 타입 토글 · 필터 칩 · 검색. **세 화면 모두 존재한다**
- **3 테이블 카드** — 흰 카드, 라운드 15(`--r-xl`), 표준 그림자
- **4 푸터** — 좌측 건수 표기 + 우측 페이지네이션

### 3.2 페이지 컨테이너

인라인 스타일 3종(`padding: 24` · `fontFamily: 'sans-serif'` · `background: '#F8F9FA'`)을 모두 걷어낸다.

| 항목 | 값 |
|---|---|
| 좌우 패딩 | `2rem` (20px) — 대시보드 5탭과 동일 |
| 콘텐츠 가용 폭 | `116rem` (1160px) |
| 배경 | 전역 `--bg` 상속 |
| 폰트 | 전역 상속 (Inter) |

### 3.3 슬롯 치수

| 슬롯 | 높이 |
|---|---|
| 페이지 헤더 | `5.6rem` (56px) |
| 툴바 | `4.8rem` (48px) |
| 테이블 카드 | 나머지 |
| 푸터 | `6.4rem` (64px), 테이블 카드 내부 하단 |

### 3.4 헤더 슬롯

**영문 부제를 삭제한다.** 기능이 없는 마케팅 문구이며 화면당 시각 요소를 하나씩 늘린다.

**타이틀은 한글만 쓰고 사이드바 탭 라벨과 일치시킨다.** 현행은 사이드바가 "배터리 목록"인데 페이지 제목이 "배터리별 점검 기록 (Battery History)"이라 같은 곳인지 확신이 서지 않는다.

| 화면 | 타이틀 | 우측 액션 |
|---|---|---|
| 배터리 목록 | `배터리 목록` | 없음 |
| 일일 리포트 | `일일 리포트` | `+ 리포트 생성` |
| 개별 리포트 | `개별 리포트` | 없음 |

`+ New Query` 버튼은 삭제한다. 핸들러도 없고 기능 정의가 명세 어디에도 없다.

`Export CSV`는 **이번 범위에서 제외한다.** 클라이언트로 구현할 수는 있으나 로드분만 내보내는 반쪽이 된다. 서버 페이지네이션이 붙은 뒤 후속으로 다룬다(§12).

### 3.5 툴바 슬롯

한 줄에 좌→우로 배치한다.

| 화면 | 구성 |
|---|---|
| 배터리 목록 | 판정 칩 · (결함 유형 칩 — 숨김) · 검색 |
| 일일 리포트 | 타입 토글 · 상태 칩 · 검색 |
| 개별 리포트 | 타입 토글 · 상태 칩 · 정렬 토글 · 검색 |

`ReportTypeToggle`(일일/개별)을 헤더 액션 자리에서 **툴바로 내린다.** 타입 전환은 성격상 필터와 같은 줄에 있는 것이 맞다.

검색 입력은 툴바 우측 끝에 고정하고 폭은 `24rem`(240px)로 둔다.

## 4. 배터리 목록

### 4.1 툴바

**판정 칩 (활성)**

| 칩 | 값 | 배지 색 |
|---|---|---|
| 전체 | — | 뉴트럴 |
| PASS | `latestFinalLabel === 'PASS'` | `#1e7e34` |
| REJECT | `latestFinalLabel === 'REJECT'` | `#d97706` |
| FAIL | `latestFinalLabel === 'FAIL'` | `#dc2626` |

칩 안에 건수를 함께 표기한다(`REJECT 5`). 대시보드 완료탭(§5.5)과 동일한 어휘다.

현행 탭은 전체/불량/검사실패 3개로 **PASS만 보는 선택지가 없었다.** 칩 4개로 그 구멍을 메우고 완료탭과 축을 일치시킨다.

**결함 유형 칩 (숨김)**

FR-LIST-003("결함 유형 4종 필터링")이 Must이나 데이터가 없다. `BatteryListItem`에 결함 유형 필드가 없고 `GET /battery`에 필터 파라미터도 없다.

규격만 정의하고 **데이터가 붙기 전까지 화면에 표시하지 않는다.** 비활성 칩을 보여주면 어수선하고, 사용자가 왜 눌리지 않는지 묻게 된다.

| 칩 | 코드 |
|---|---|
| 전체 | — |
| 갈라짐 | `CRACK` |
| 오점 | `SPOT` |
| 미세결함 | `MICRO_DEFECT` |

**`SWELLING`(부풀음)은 칩에서 제외한다.** 코드표에는 있으나 이를 출력하는 모델이 없어 항상 0이다(Core §6.5). 4종 코드표는 가능한 값의 사전이지 화면 목록이 아니다.

**검색** — `cellSerialNo` 대상. 부분 일치, 대소문자 무시, 디바운스 300ms.

### 4.2 컬럼

```
셀 시리얼 · 모델 · 셀 유형 · 최근 검사 · 판정
```

| 컬럼 | 필드 | 표현 |
|---|---|---|
| 셀 시리얼 | `cellSerialNo` | mono. `null`이면 `CELL-{batteryCellId}` |
| 모델 | `modelName` | 텍스트. `null`이면 `-` |
| 셀 유형 | `cellType` | 배지. **`POUCH` · `CYLINDRICAL` 2종** |
| 최근 검사 | `latestAnalyzedAt` | `YYYY-MM-DD HH:mm`. `null`이면 `-` |
| 판정 | `latestFinalLabel` | 배지 (§6) |

**`#` 컬럼과 `상세` 컬럼을 삭제한다.** `#`는 클라이언트 슬라이스 순번이라 페이지를 넘기면 의미가 바뀐다. `상세`는 행 클릭과 중복이며, FR-LIST-005가 "행 클릭 시 상세 이동"을 Must로 규정하므로 행 클릭이 정본이다.

행 hover 시 우측 끝에 chevron을 표시한다. 컬럼이 아니라 hover 시에만 나타나는 시각 힌트다.

`cellType`에 `PRISMATIC`을 두지 않는다. Core §10.3이 존재하지 않는 셀 타입으로 확정했다.

### 4.3 정렬

**정렬 UI를 두지 않는다.** `GET /battery`에 `sort` 파라미터가 없다. 클라이언트 정렬은 로드분 안에서만 도는 반쪽이라 §2.3에 어긋난다.

## 5. 리포트 목록

### 5.1 라우트 구조

현행 2개 라우트(`/reports/daily` · `/reports/individual`)를 유지한다. 타입 전환은 툴바의 토글이 담당한다.

> **후속 전환 가능성** — 두 라우트를 `/reports` 하나로 합치고 타입을 필터 축으로 흡수하는 안을 검토했다. 대시보드 완료탭에서 "서브카드 병렬 → 필터 1축" 전환을 확정한 것과 같은 패턴이며, 두 테이블의 복붙 구조(§1.4)를 구조적으로 없앨 수 있다. 이번에는 채택하지 않았으나 **추후 전환할 수 있다.** 비교용 시안을 `04-report-unified-explore.svg`로 함께 제공한다.

### 5.2 툴바

**타입 토글** — `일일` / `개별`. 라우트 이동을 트리거한다.

**상태 칩**

| 칩 | 값 |
|---|---|
| 전체 | — |
| 완료 | `COMPLETED` |
| 대기중 | `PENDING` |
| 실패 | `FAILED` |

**정렬 토글** — `최신순` / `오래된순`. `GET /reports/*?sort` 파라미터를 사용한다. 리포트 목록에만 존재한다.

**검색** — `title` 대상.

### 5.3 일일 리포트 컬럼

```
상태 · 제목 · 판정일자 · 생성일시
```

| 컬럼 | 필드 | 표현 |
|---|---|---|
| 상태 | `status` | 배지 (§6.2) |
| 제목 | `title` | 텍스트. `null`이면 `리포트 #{reportId}` |
| 판정일자 | `reportDate` | `YYYY-MM-DD` |
| 생성일시 | `createdAt` | `YYYY-MM-DD HH:mm` |

### 5.4 개별 리포트 컬럼

```
상태 · 제목 · 대상 셀 · 회차 · 생성일시
```

`대상 셀`과 `회차` 두 컬럼은 **BE 협의가 필요하다.**

| 컬럼 | 필요 데이터 | 현재 |
|---|---|---|
| 대상 셀 | `batteryCellId` | **없음** — Core §10.5가 이미 갭으로 등재 |
| 회차 | `batteryCellId` + `createdAt` 순번 | **없음** (회차는 셀별 순번이라 셀을 모르면 계산 불가) |

이 갭이 특히 아픈 이유는 회차가 셀당 **무제한 증가**하기 때문이다(FR-REPORT-006, B-3). 같은 셀의 리포트가 5회차까지 쌓이면 목록에 5개 행이 나오는데, **구별할 단서가 LLM 생성 제목뿐이다.** 제목은 자유 텍스트라 형식이 보장되지 않고, `null`이면 `리포트 #12`로 폴백되는데 그것은 리포트 ID지 셀 ID가 아니다.

`title`에서 셀 번호를 파싱하는 방법은 **채택하지 않는다.** 파싱이 조용히 실패하면 잘못된 셀 번호를 표시하게 된다.

**폴백** — 협의 전까지 두 컬럼을 `수정일시`(`updatedAt`) 한 컬럼으로 대체한다.

```
상태 · 제목 · 수정일시 · 생성일시
```

### 5.5 리포트 생성

**일일 리포트** — 목록 헤더 우측에 `+ 리포트 생성` 버튼을 둔다. 클릭하면 날짜 피커 팝오버가 열리고, 날짜를 고르면 `POST /reports/daily { reportDate }`를 호출한다.

**개별 리포트** — 리포트 목록에 두지 않는다. **배터리 상세 화면에서 생성한다.**

근거는 세 가지다.

1. 생성 대상이 **REJECT 또는 FAIL 검사에 한정**된다(Core §4.8). 목록 행마다 액션 유무가 달라지면 목록이 들쭉날쭉해진다.
2. 배터리 상세에는 그 셀의 `inspections[]`와 `reports[]`가 모두 있다. "이 셀은 REJECT이고 기존 리포트가 2회차까지 있다"를 보면서 3회차를 만드는 흐름이 맥락상 정확하다.
3. 목록에서 바로 만들면 기존 리포트 존재 여부를 모른 채 중복 생성하기 쉽다.

> **후속 전환 가능성** — 배터리 목록 행에 hover 보조 액션으로 생성 진입점을 추가하는 안도 검토했다. 이번에는 행 클릭 단일 어포던스를 지키기 위해 채택하지 않았으나, 사용 빈도가 높다고 판단되면 **추후 추가할 수 있다.** 그 경우 PASS 행에서 액션이 사라지는 문제를 함께 설계해야 한다.

배터리 상세 화면 자체는 이 문서의 범위 밖이다. 생성 버튼의 배치 규격은 해당 화면 설계 시 정한다.

## 6. 상태 표현

### 6.1 형태 — 배지

dot + 텍스트가 아니라 **배지**(pill + 배경 틴트 + 텍스트)를 쓴다. 대시보드 완료탭 행·탐지 카드와 동일한 어휘여야 같은 값이 화면마다 다른 모양으로 보이지 않는다.

| 항목 | 값 |
|---|---|
| 높이 | `2.4rem` (24px) |
| 좌우 패딩 | `1.0rem` (10px) |
| 라운드 | `999px` (`--r-pill`) |
| 폰트 | `1.15rem` mono, letter-spacing 0.05em |

### 6.2 색 매핑

색 값의 원 소유자는 `BRAND_COLOR.md` §5.2다. 이 문서는 인용만 한다.

**배터리 판정**

| 값 | 전경 | 배경 |
|---|---|---|
| `PASS` | `#1e7e34` | `#ecfdf3` |
| `REJECT` | `#d97706` | `#fffbeb` |
| `FAIL` | `#dc2626` | `#fef2f2` |

**리포트 상태**

| 값 | 전경 | 배경 |
|---|---|---|
| `PENDING` | `#13777C` (teal-600) | `#EBF8F9` (teal-50) |
| `COMPLETED` | `#5b5f63` (뉴트럴) | 배경 없음 |
| `FAILED` | `#dc2626` | `#fef2f2` |

두 화면의 상태값은 **서로 다른 축**이다. 배터리는 검사 판정(셀이 정상인가), 리포트는 문서 생성 진행(리포트가 만들어졌나)이다.

`COMPLETED`를 초록이 아니라 뉴트럴로 두는 근거는 두 가지다.

1. **초록이 거짓말을 한다.** 개별 리포트는 REJECT 또는 FAIL 검사에만 생성된다(Core §4.8). 초록 배지가 붙은 행의 대상은 전부 불량 셀이다. "초록 = 괜찮음"으로 읽히면 정면으로 틀린다.
2. **`COMPLETED`가 다수다.** 리포트 목록의 대부분 행이 완료 상태다. 다수에 색을 칠하면 색이 정보가 아니라 배경이 된다. 주의가 필요한 것은 `PENDING`(기다려야 함)과 `FAILED`(재시도해야 함)이고, 그 둘만 색을 갖는 것이 스캔에 유리하다.

`PENDING`에 PROCESS 청록을 쓰는 것은 의미가 맞기 때문이다. `PENDING`은 LLM이 지금 돌고 있는 상태이며, 대시보드에서 "진행 중 = PROCESS"를 확정했다.

### 6.3 REJECT / FAIL 이중 부호화

`BRAND_COLOR.md` §9가 미결로 남긴 색상각 이격 부족이 **목록 화면에서 가장 크게 드러난다.**

| 쌍 | ΔH | 판정 |
|---|---|---|
| REJECT `#d97706` ↔ FAIL `#dc2626` | 31도 | 부족 |

대시보드에서는 둘이 누적 100% 바의 서로 다른 구간이라 위치로도 구분되었다. **목록은 다르다.** 배터리 목록에서 REJECT 행과 FAIL 행이 위아래로 인접하고, 같은 컬럼 같은 위치에 배지만 다른 색으로 놓인다. 31도 차이를 세로로 스캔하며 구별해야 한다. REJECT는 흰 배경 대비도 3.19로 WCAG AA에 미달한다.

**색에만 의존하지 않는다.** 배지에 형태 차이를 함께 준다.

| 값 | 형태 |
|---|---|
| `PASS` | 채운 배지 (배경 틴트 + 전경 텍스트) |
| `REJECT` | 채운 배지 + **좌측 채운 원형 마커** |
| `FAIL` | **테두리 배지**(배경 없음, 1px 실선) + **좌측 삼각 경고 마커** |

색 자체는 바꾸지 않는다. `BRAND_COLOR.md` §9가 REJECT 색을 미결로 남겼고 그것은 브랜드 문서의 소유 사안이다. 이 문서가 색을 바꾸면 SSOT가 둘로 갈린다.

이중 부호화는 색 결정을 기다리지 않고 지금 확정할 수 있으며, 나중에 REJECT 색이 바뀌어도 형태 규칙은 그대로 유효하다. 적록색약에서 주황과 빨강은 가장 흔하게 겹치는 쌍이므로 접근성 측면에서도 필요하다.

> **브랜드 문서에 피드백할 것** — REJECT와 FAIL이 목록에서 인접 배치되므로 `BRAND_COLOR.md` §9의 "REJECT 색 자체" 미결은 우선순위가 높다.

### 6.4 셀 유형 배지

| 값 | 표기 |
|---|---|
| `POUCH` | `파우치` |
| `CYLINDRICAL` | `원통형` |

판정·상태와 구별되어야 하므로 **뉴트럴 배지**로 그린다(전경 `#5b5f63`, 배경 `#f3f4f6`). 상태 5색을 쓰지 않는다.

### 6.5 실패 사유는 목록에 노출하지 않는다

`FAILED` 행에 사유를 함께 보여주는 것을 검토했으나 **목록 응답에 필드가 없다.** `BatteryListItem` · `DailyReportListItem` · `IndividualReportListItem` 어디에도 `failureReason`이 없다. 툴팁으로 넣으려 해도 데이터가 없다.

사유는 상세 화면에서 확인한다. 두 집합이 서로 다르므로 섞지 않는다(§0.2).

### 6.6 브랜드 컬러 사용 범위

브랜드 블루 `#0C5795`는 목록 화면에서 다음 자리에만 쓴다.

| 자리 | 값 |
|---|---|
| 사이드바 활성 탭 | `#0C5795` (brand-700) |
| `+ 리포트 생성` 버튼 | `#0C5795`, 호버 `#236CAE`, 프레스 `#054477` |
| 활성 필터 칩 | `#0C5795` 배경 + 흰 텍스트 |
| 행 hover 배경 | `#EEF6FE` (brand-50) |

판정·상태 표현에는 브랜드 컬러를 쓰지 않는다(`BRAND_COLOR.md` §8).

## 7. 상태 변형

### 7.1 로딩 — 스켈레톤

테이블 구조를 유지한 채 셀만 회색 바로 채운다. **행 8개**를 표시한다.

현행은 `로딩 중...` 텍스트가 테이블 위에 뜨고 테이블은 그대로 렌더되므로, 로딩이 끝나면 텍스트가 사라지며 높이가 튄다. 스켈레톤은 최종 레이아웃과 같은 높이라 시프트가 없다.

| 항목 | 값 |
|---|---|
| 바 높이 | `1.4rem` (14px) |
| 바 색 | `#eceef0` |
| 라운드 | `999px` (`--r-pill`) |
| 폭 | 컬럼별로 다르게 (60~90%) — 균일하면 기계적으로 보인다 |

툴바와 헤더는 스켈레톤으로 덮지 않는다. 필터 조작은 로딩 중에도 가능해야 한다.

### 7.2 빈 상태 — 두 경우를 구분한다

| 경우 | 문구 | 액션 |
|---|---|---|
| 데이터 자체가 0건 | 배터리: `아직 검사된 배터리가 없습니다`<br>리포트: `생성된 리포트가 없습니다` | 일일 리포트만 `+ 리포트 생성` |
| 필터·검색 결과가 0건 | `조건에 맞는 항목이 없습니다` | `필터 초기화` |

구분하는 이유는 **두 경우의 해결책이 정반대**이기 때문이다. 전자는 기다리거나 만들어야 하고, 후자는 필터를 풀어야 한다. 같은 문구를 쓰면 사용자가 필터를 켜놓은 것을 모르고 "데이터가 없다"로 오해한다.

현행 배터리 목록에는 빈 상태 처리가 아예 없어 "불량 이력" 탭 결과가 0이면 헤더만 남은 빈 테이블이 나온다.

### 7.3 에러

테이블 자리를 에러 블록으로 대체한다.

| 요소 | 내용 |
|---|---|
| 문구 | `목록을 불러오지 못했습니다` |
| 보조 문구 | 스토어의 `error` 값 |
| 액션 | **`다시 시도` 버튼** |

`FUNC_SPEC` §1.4가 "조회 실패 시 에러 메시지 표시(자동 재시도 없음)"로 못박았으므로, **수동 재시도 수단이 없으면 새로고침 외에 방법이 없다.**

### 7.4 푸터

| 상황 | 처리 |
|---|---|
| 결과 0건 | 페이지네이션 컨트롤을 **숨긴다**. 건수는 `0건`으로만 표기하고 범위는 생략 |
| 로딩 중 | 건수·페이지네이션을 스켈레톤으로 |

현행 `Pagination`은 `totalPages = Math.max(1, ...)`라 0건에도 `1` 버튼이 홀로 뜬다.

| 방식 | 부분 일치, 대소문자 무시 |
| 초기화 | 입력값이 있을 때 우측에 `×` |
| 페이지 | 검색어 변경 시 1페이지로 리셋 |

요청이 나가지 않고 로드된 배열을 대상으로 하므로 즉시 반영이 자연스럽다.

### 8.4 정렬

리포트 목록에만 존재한다. `최신순` / `오래된순` 토글이며 `GET /reports/*?sort`를 사용한다.

### 8.5 페이지네이션

| 항목 | 값 |
|---|---|
| 페이지 크기 | 20 고정 |
| 크기 선택 UI | **두지 않는다** — 서버 페이지네이션이 없는 상태에서 크기 선택은 클라이언트 슬라이스만 바꾸는 눈속임이다 |
| 건수 표기 | `47건 중 1–20` |

건수 표기를 한글로 바꾸는 이유는 두 가지다. 현행 `Showing 1 to 20 of 47 entries`는 **총계처럼 읽히지만 실제로는 로드분**이며(§1.5), 타이틀이 한글인데 푸터만 영문이라 톤이 튄다.

서버 필터·페이지네이션이 붙으면 이 문구는 그대로 총계 의미로 승격된다.

둘 다 화면 설계는 완료되어 있으며 데이터가 붙는 즉시 표시할 수 있다.
